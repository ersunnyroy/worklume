# E12-S01 spike: X11 APIs

**Question.** Can the Linux agent on X11 measure idle time and input, read the active window
and browser addresses, and capture screens, without special permissions and at an acceptable
cost?

**Answer.** Mostly yes.

- **Go** for idle time, input, the active window and screen capture (E12-S02, E12-S03 and the
  window part of E12-S04).
- **No-go for AT-SPI as the main source of browser addresses.** On X11, addresses have to come
  from the browser extension (E35), which is planned for V1. This needs a scope decision (see
  "Browser addresses").
- **A gap in the backlog:** nothing detects a locked session on Linux. That matters for
  privacy, because X11 delivers input to the agent even on the lock screen (see "Session
  lock").

## How it was tested

- Ubuntu 24.04, run in the cloud workspace:
  - Xvfb 21.1.12 (MIT-SHM, `XInputExtension` 2.4, MIT-SCREEN-SAVER, RANDR 1.6 and X-Resource
    1.2 all present);
  - Openbox 3.6.1 as an EWMH window manager;
  - a D-Bus session and at-spi2-core 2.52;
  - Chromium 141.0.7390.37 and xterm.
- Input came from `xdotool` (XTEST), and monitors were defined with `xrandr --setmonitor`.
- A throwaway probe used `x11rb` 0.13.2 with its pure-Rust connection, so no `libX11` or
  `libxcb` is linked. A small Python script used AT-SPI (`gir1.2-atspi-2.0`). Neither is kept.
- **Not tested:**
  - real GNOME and KDE X11 sessions, including compositing;
  - real keyboards, mice and touchpads (smooth scrolling);
  - Firefox;
  - remote-desktop servers;
  - multiple X screens.

  These belong to the E12 test matrix (Ubuntu 22.04 and 24.04, GNOME and KDE).

## Verdict

| Area           | API                                                 | Verdict                  | Cost measured                                                 |
| -------------- | --------------------------------------------------- | ------------------------ | ------------------------------------------------------------- |
| Idle time      | MIT-SCREEN-SAVER `QueryInfo`                        | Go                       | Under 0.3 ms per reading                                      |
| Input events   | XInput 2.2 raw events on the root window            | Go, with two conditions  | Event-driven; nothing per tick                                |
| Active window  | EWMH `_NET_ACTIVE_WINDOW`, `WM_CLASS`, X-Resource   | Go                       | Usually 0.15–1 ms per reading                                 |
| Screen capture | MIT-SHM `GetImage` per RandR 1.5 monitor            | Go                       | 1.5 ms per 1920×1080 monitor, 2.5 ms at 2560×1440             |
| Browser URLs   | AT-SPI                                              | No-go as the main source | 74 ms to walk a trivial page's tree when it is exposed at all |
| Session lock   | None in X11; logind and screen-saver D-Bus services | Not covered by any story | Not measured (no logind in the workspace)                     |

No X11 API here needs a permission, a prompt or root. X11 lets any client read input and the
screen. The agent therefore has to hold itself to its rules: kind and time of input only,
never key codes or pointer positions.

## Idle time

`screensaver_query_info(root).ms_since_user_input` resets on any keyboard or pointer input,
including XTEST input. Each reading took under 0.3 ms. It implements `IdleSource` directly.

## Input events (E09-S13's `InputActivity`)

Select `RawKeyPress`, `RawButtonPress` and `RawMotion` on the root window for all master
devices. Raw events need XInput 2.2; the server had 2.4. The events map as follows:

| X11 event                  | `InputKind` | Tested                                            |
| -------------------------- | ----------- | ------------------------------------------------- |
| `RawKeyPress`              | `Key`       | 6 of 6 key presses                                |
| `RawButtonPress` 1–3, 8, 9 | `Click`     | 2 of 2 clicks                                     |
| `RawButtonPress` 4–7       | `Scroll`    | 3 of 3 wheel notches                              |
| `RawMotion`                | `Pointer`   | 5 of 5 relative moves; **0** absolute XTEST moves |

- **Auto-repeat doesn't reach raw events.** A key held for 1.5 s with repeat on (660 ms delay,
  25/s) gave exactly one `RawKeyPress`, which is what `InputKind::Key` requires.
- **The key code is in the event** (`detail`). The reader must drop it where it reads the event
  and keep only the kind and the time.
- **Smooth scrolling isn't settled.** Touchpads and high-resolution wheels report scrolling as
  `RawMotion` on scroll valuators, plus emulated buttons 4–7 flagged `POINTER_EMULATED`. The
  reader should read the scroll classes from `XIQueryDevice`, count scroll-valuator motion as
  `Scroll`, and skip the emulated buttons, or the other way round. Xvfb has no such device, so
  this is for E12-S03 on real hardware.
- **The reader runs on its own thread with its own connection,** blocking in `wait_for_event`,
  and buffers events for the agent's one-second drain.

**Condition 1: input arrives even when another client holds a grab.** While a second client
held both the keyboard and the pointer, as screen lockers do, the reader still saw every key
of "secret" typed into it. On a lock screen the agent would therefore see when a password is
typed. It must not record input while the session is locked (see "Session lock").

**Condition 2: absolute XTEST motion produces no raw motion.** Keys and clicks sent through
XTEST do. Some remote-desktop servers inject input this way, so remote sessions may under-count
pointer activity. Idle time is unaffected. Real absolute devices (tablets, VM tablets) go
through the input driver and should produce raw motion; E12-S03 should check a VM and one
remote-desktop server.

The E12-S03 criterion "a combined keyboard and mouse figure where the split is unavailable"
applies only when XInput 2.2 is missing. Then the agent can only derive activity from
`ms_since_user_input`.

## Active window (E09-S12's `ActiveWindow`)

- `_NET_ACTIVE_WINDOW` on the root window gives the window, and 0 means none.
- `WM_CLASS` gives the application. **Use only its class part** ("Chromium-browser", "xterm").
  The instance part can hold a path: Chromium started with `--user-data-dir` put the profile
  path in it.
- **The PID comes from X-Resource** (`QueryClientIds` with `LOCAL_CLIENT_PID`). That is the
  server's own record. `_NET_WM_PID` is set by the client and may be missing or wrong. Both
  agreed in every test. `/proc/<pid>/exe` then gives the executable.
- `ForegroundApp.identifier` should be the desktop-file ID. Find it by matching `WM_CLASS` to
  `StartupWMClass`, or the executable to `Exec`, in the XDG `.desktop` files. Fall back to the
  lower-cased class.
- The title is `_NET_WM_NAME` (UTF-8), falling back to `WM_NAME` (xterm sets only `WM_NAME`).
  Read it only when asked (`with_title`).
- **Poll it on each tick rather than follow events.** Switching between three windows produced
  eight `PropertyNotify` events on the root. They included a transient 0 between windows and
  repeats of the same value. Title changes don't notify the root at all, since titles are
  properties of the window. A reading took 0.15–1 ms (once 3.9 ms) with about a dozen round
  trips. Half of them were atom lookups, which the adapter looks up once and keeps.

## Screen capture (E12-S02)

- `randr_get_monitors` (RandR 1.5) lists each monitor's rectangle. The test used two monitors
  of different sizes, 1920×1080 and 640×1440, and each was captured correctly.
- **MIT-SHM is ten times faster than a plain `GetImage`.** The server writes into a shared
  `memfd`, and only a reply header crosses the socket:

  | Area      | `GetImage` | MIT-SHM `GetImage` |
  | --------- | ---------- | ------------------ |
  | 1920×1080 | 16 ms      | 1.5 ms             |
  | 640×1440  | 2.5 ms     | 0.7 ms             |
  | 2560×1440 | 26 ms      | 2.5 ms             |

  The buffer is 4 bytes per pixel (8 MB at 1080p).

- Mapping the shared memory needs one `unsafe` block (`mmap`). The adapter opts in with a
  `SAFETY:` comment, as `docs/conventions/tooling.md` expects.
- Fall back to plain `GetImage` when MIT-SHM is missing or refuses, for example on an X server
  reached over SSH forwarding.
- **Monitors can overlap.** RandR returned Xvfb's whole-screen monitor alongside the two defined
  ones. Mirrored displays overlap in the same way, so the adapter must skip monitors contained
  in another before capturing.
- Capture on composited GNOME and KDE X11 desktops is for E12-S02's test matrix.

## Browser addresses (E09-S12's `BrowserUrl`)

When Chromium exposes its tree, the address is there:

- The web document's `URI` attribute holds the full address
  (`http://127.0.0.1:8765/project/board.html?id=42`).
- The address bar entry holds it without the scheme.

It was exposed in only one of the six setups tried:

| Setup                                                                   | What AT-SPI showed                                  |
| ----------------------------------------------------------------------- | --------------------------------------------------- |
| Accessibility off (the default), browser started normally               | Nothing: Chromium doesn't register                  |
| Accessibility switched on after the browser started                     | Nothing: Chromium decides at launch                 |
| Accessibility on before launch                                          | The window frame only, no children                  |
| Accessibility and "screen reader" on before launch                      | The window frame only                               |
| Accessibility on, and the probe listening for events as a screen reader | The window frame only                               |
| Chromium started with `--force-renderer-accessibility`                  | Full tree: address bar and document URL (225 nodes) |

**Verdict: no-go as the main source.**

- The agent can't make a browser that is already running expose its address.
- The agent can't make a browser expose it at launch without changing how the member starts
  the browser.
- Turning accessibility on for the whole desktop would change every application and cost CPU
  and memory in each.
- Where AT-SPI is already on and the browser exposes its tree (a member using a screen
  reader, and possibly Firefox, which is untested), the agent can use it. It should look the
  document up directly (the Collection interface) rather than walk the tree.

**Rejected:**

- Reading the browsers' session or history files. That reads the member's whole history, not
  the tab in front, and breaks between browser versions.
- Guessing addresses from window titles. Titles hold the page title, not the address.

**The decision this needs.** Until the browser extension (E35, V1) ships, the X11 agent in
Private Beta can't record addresses. It reports them as unavailable in the capability report
(E09-S06) rather than guessing. There are two ways to handle that:

- Accept it for Private Beta.
- Bring the Chrome and Firefox part of E35 forward to Private Beta. Wayland needs it anyway
  (E13 depends on E35).

E12-S04's criterion, "falls back to the extension when AT-SPI is off", still holds. In practice
the extension becomes the main path and AT-SPI the exception.

## Session lock

X11 has no lock event: screen lockers are ordinary clients. On Linux the lock state comes from
D-Bus:

- logind's `LockedHint` on the member's session (`org.freedesktop.login1.Session`), which
  GNOME and KDE set;
- `ActiveChanged` from `org.freedesktop.ScreenSaver` or `org.gnome.ScreenSaver` for other
  lockers.

The tracker already supports `pause(SessionLocked)`, and "Idle and sleep" in
`docs/conventions/desktop.md` leaves wiring it to the per-OS stories. No E12 story names it,
and condition 1 above makes it a privacy requirement on X11. **Recommendation:** add it to
E12-S03, the input story, as "no input is recorded while the session is locked, and the timer
pauses with reason `session_locked`". It lives in the shared `linux::power` module, so Wayland
reuses it. The workspace has no logind, so the spike couldn't test it.

## Crates for E12

- `x11rb`, pure-Rust connection, features `xinput`, `screensaver`, `shm`, `randr` and `res`.
  The probe built with it on the first try.
- `memmap2` for the capture buffer.
- `zbus` for logind and the screen-saver services.
- `atspi` (on `zbus`) only for the opportunistic address reading.
